TL;DR

One task group, one file, one execution wave: overwrite profile/README.md with the verbatim "Exact Replacement Content" block already pinned in implementation/spec.md, re-stage it in git, and run the 7 manual verification checks the spec itself defines (no automated test suite applies to this docs-only repo). No dependencies, no parallelism to schedule, no Testing Review group — this is deliberately not broken up further than the single action it is.

Key Decisions

  • Single task group — the entire scope is one file overwrite plus checks of that same content; splitting would add coordination overhead with zero parallelism benefit for a 1-file change.
  • "Define checklist" replaces "write tests" — no automated test suite exists for this repo (docs-only, no build step). The spec's own 7-item manual checklist fills the same role, within the standard 2-8-per-group convention.
  • No Testing Review group — that group only applies when total implementation groups ≥ 3; with exactly 1 group here it would be pure overhead.

Open Questions / Risks

  • M-1Literal reading of "git status shows only profile/README.md staged" is unachievable — 3 unrelated files are already staged pre-task. Step 1.4(c) checks the delta this task introduces, not the absolute staged-file count.
  • M-2After this overwrite, standards/profile/markdown-authoring.md and structure.md will contain stale example citations. Out of scope for this task's implementation; flagged for operator follow-up.
  • deferredCalendar link reachability and the GitHub-native post-merge rendering check are both explicitly deferred per spec's Out of Scope — logged as informational in step 1.4, not gating.
